# Card-table runtime audit — October 15, 2026

Audited baseline: `33b5c0f`. Scope: source review, production build, local desktop Chromium tests at desktop/phone viewport sizes, and architecture planning. No gameplay or artwork changes made in this audit. No physical OnePlus GPU reproduction was available; the reported black-card defect remains unresolved.

## Conclusion

The product has a useful foundation: a React SPA shell, standalone manifest, working Solitaire, four-player UNO, audio/preferences, Solitaire checkpoints, offline/update support, and an initial ghost mode. It does not yet have a shared game-table engine. Use TypeScript and incremental extraction to create one, proving every shared abstraction against Solitaire and UNO before adding games.

The next visible feature should be Solitaire's card flourishes and haptics, per the latest user priority. Diagnose the black-card problem first or in an isolated diagnostic track; do not compound an unresolved device renderer failure with elaborate new GPU effects. Preserve the original intro.

## Findings, ordered by priority

### High: OnePlus black cards are not covered by current validation

`games/solitaire/card-visuals.js:3` creates normal image elements; `games/solitaire/solitaire.css:7` supplies opaque paper and CSS backgrounds for backs. Gameplay is not drawn by the custom shader. The WebGL shader is `src/intro-shader.js:2`, used by the title scene. There is also a separate canvas particle layer and decorative logo card fan.

Image fallback relies on load/decode success and a 15-second timeout. Successful decoding does not prove the GPU/compositor displayed the pixels correctly. Missing-image fallback will not catch that class of failure. Desktop screenshot tests cannot validate an Android GPU driver.

Required diagnostic: identify which layer fails, record app release/browser/OS/device versions, compare raw images, static opaque cards, moving/clipped cards, and the same scene with visual effects disabled. Keep file URLs, requests, decoded dimensions, computed styles, and screenshots. Test a real failing OnePlus and a known-working device. Texture upload/compositing, clipping, resource pressure, and stale resource combinations are hypotheses, not established causes. Do not label a speculative CSS change a confirmed fix.

### High: games are separate controllers, not extensions of a shared runtime

`src/main.jsx:81` and `:92` mount different controllers with `window.__sol` / `window.__uno`. Solitaire combines state transitions, persistence, rendering, input, layout and effects in one controller. UNO has its own shuffle, turn scheduler, card representation, rendering and AI. `assets/js/game-primitives.js` already provides seeded shuffling, but UNO uses its own `Math.random` shuffle (`games/uno/uno.js:35`).

Extract ownership/lifecycle, zones, input commands, stable card identities, layout, animation events, clock, seeded randomness, checkpoints, asset lookup and audio services. Game-specific legality, scoring and turn phases belong in each extension. Avoid a universal rules class or a second framework.

### High: UNO cannot preserve a round like Solitaire

`games/uno/uno.js:230` starts a new round on every mount. It has no checkpoint or replay interface. `assets/js/sw-register.js` explicitly postpones updates until UNO finishes for this reason. Generic tutorial, replay and update support must begin with deterministic UNO state and complete lifecycle cleanup. Distinguish individual duplicate UNO cards with stable instance IDs.

### High: TypeScript migration requires changing module delivery

`src/main.jsx:13` imports engine/audio modules through `@vite-ignore`; `tools/build-pwa.mjs` copies raw source directories into the deployed app. Renaming these modules to `.ts` will not make browsers execute TypeScript. Move engines into explicit Vite-managed lazy imports and generate the offline manifest from emitted assets. Add a separate `tsc --noEmit` check; Vite transpilation alone does not type-check.

### Medium: update handling works, but lacks release-level integrity and observability

Settings → App already includes Check for updates, Refresh app cache and Erase saved data. Startup, foreground and periodic checks exist. An actual service-worker upgrade preserved a Solitaire checkpoint in this audit's local test.

`src/app-storage.js:7` infers “up to date” from worker state immediately after an update check. It does not compare a displayed running release against an installed/available release or track later installation failure. Add explicit checking/downloading/ready/failed states and running/available versions.

`sw.js` activates immediately and serves unversioned JS/CSS network-first; raw engine files are not revisioned bundles. This creates a potential mixed-release window and deserves an update-atomicity test. Cache refresh deletes app caches without reinstalling an unchanged worker; verify complete offline readiness afterward rather than assuming it. Never erase saves as an update remedy.

### Medium: ghost recording exists, but needs durability and presentation work

`games/solitaire/replays.js` records initial state, post-action snapshots and active timestamps. `src/ghost.jsx` replays the same deal beneath the live board. This is an existing feature to preserve, not a new feature to recreate.

The panel is currently compact, not half the screen. Recorded actions are capped at 2,000; truncated runs are excluded from choices. The archive retains up to 12 runs with an approximate 1.5-million-character budget, except the newest run may exceed it. `saveReplay` silently catches storage errors. `saveGame` repeatedly serializes the replay archive and history through synchronous localStorage. This is a scaling/performance risk on the Moto, not a measured frame-time result from this audit.

Move toward versioned, transactional IndexedDB storage with bounded retention and explicit recording failures. Preserve existing recordings through migration. Define completed/practice/assisted categories. Same-deck races are the fair default; different-deck races should be labeled casual challenges. Use a shared active clock and persist the opponent identity. Make the bottom region expandable while protecting live-card touch size.

### Medium: lifecycle cleanup needs a single owner

Solitaire cleanup (`games/solitaire/solitaire.js:485`) does not remove `window.__sol`, whereas UNO deletes its global handle. The shell calls the old Solitaire save handle during navigation. Refactor to owned, disposable instances; verify no old controller can advance time, save, animate or emit sounds after another game takes over. Review delayed rewind/deal/effect callbacks during navigation.

### Medium: continuous integration builds but does not gate on the existing checks

`.github/workflows/pages.yml` installs, builds and publishes. It does not run the rules, replay, runtime or persistence tests. Several tests hardcode the developer's Windows dependency path. Make the meaningful tests portable and require them, type-checking and artwork integrity checks before deployment.

## Proposed shared system

| Owner | Responsibilities |
| --- | --- |
| App shell | One URL, Home/Game Select, settings, installation, safe areas, update UI |
| Table runtime | Session lifecycle, stable card/zone identities, commands, clock, RNG, saves, event journal |
| Table renderer | Card visibility, hands/piles/layout, input mapping, transitions, readable fallback |
| Environment | Table material, floor, edge, lighting/reflection layers, restrained tilt |
| Game extension | State schema, deck recipe, legal actions, reducer, turn phases, scoring, AI and rule version |
| Tutorial runner | Seeded scenarios, spotlight targets, explanations, accepted actions, step advancement, separate progress |
| Asset/audio catalog | Shared protected art and licensed sounds, semantic event cues, game-specific presentation presets |

UNO's colored cards and a standard playing deck share identity/zone mechanics without pretending their card values are identical. Poker adds betting phases and hidden-information views; rummy adds melds. AI and tutorials must consume only the information permitted to their role.

## Table environments and movement

Start with green felt, blue felt and glass over wood flooring. The glass composition needs visible floor outside the table edge, floor visible through the surface, a faint tint, a highlight/reflection layer, edge thickness and soft shadows. A layered 2D/2.5D presentation can produce the intended impression with fewer dependencies than a full 3D rewrite. Stylized reflections are sufficient for the first version; do not promise physically accurate reflections.

Select a table once per new session/deal from enabled favorites. Save its ID; resume, undo, replay and React rerenders must not reroll it. Environment randomness must be separate from deal/AI randomness. Offer a fixed favorite.

Use optional, calibrated tilt with approximately 2–6 CSS pixels of relative displacement and at most 1 degree apparent tilt. Move the floor most, highlights slightly, and keep the playable card surface/input coordinates stable initially. Smooth readings, account for screen rotation, stop when hidden, respect reduced motion, and handle absent/denied sensors. Any actual transformed input surface needs inverse-coordinate hit testing.

The current intro already caps resolution and frame rate and stops after about five seconds. Preserve its design. Full 3D would add renderer, materials, GPU recovery, resolution scaling and additional device testing; do not introduce it before the compatibility gate.

## Solitaire feel, tutorials and future games

The aunt likes expressive card effects and racing/gambling-style sounds. Start with more satisfying deals, foundation arrivals, special moves and win celebrations, with brief event-aligned haptics. Keep quick routine moves readable; avoid shaking the entire UI or blocking input. Haptics are currently optional and disabled by default; retain preferences and provide a clear control. Browser vibration can be unavailable or ignored.

Use a shared asset catalog, not copied asset folders per game. Each game chooses its own choreography, audio cues and pacing. Preserve harp menu sounds. Consider chip clacks, payout flourishes, a starting bell and restrained crowd sounds only with documented licenses. A card-driven horse race is a possible later extension, not authorized priority over Solitaire.

Tutorials should let her perform each move on the real board: demonstrate, spotlight, explain briefly, accept the intended legal action, then fade. Support replay/skip and a slower teaching pace. Keep tutorial saves separate from normal games. Prove this with Solitaire and UNO. Choose explicit rummy and poker variants before implementing their rules or lessons.
